# System overview (data lifecycle)
- Zustand is the single source of truth. `useStore` defines the schema and persist config, storing under `cashflow-storage` in IndexedDB via `indexedDBStorage` (src/store/useStore.js:195-206, src/store/storage.js:3-79). `hasHydrated` guards render state and is forced to true on merge and in `onRehydrateStorage` (src/store/useStore.js:214-256, 258-264).
- Persisted state is rehydrated before any Firebase traffic; `merge` maps legacy keys (expenses/transactions, bills/recurringBills) and normalizes arrays before returning hydrated state (src/store/useStore.js:221-255). `patchSetFullPlanData` also flips `hasHydrated` after any setFullPlanData call to avoid UI waiting on persistence (src/store/useCashflowStore.js:112-126).
- Firebase listeners exist in two hooks: `useFirebaseSync` mounts an auth listener and a Firestore `onSnapshot` for the user doc (singleton per hook instance, refCount guarded) and pushes `profile` and `data` into the store (src/hooks/useFirebaseSync.js:36-110). `useCashflowData` also mounts its own auth + `onSnapshot` singleton (separate module-level guards) that hydrates local hook state and can call `setFullPlanData` on fallback; both hooks can run concurrently, so two Firestore listeners may be active even though each module self-dedupes (src/hooks/useCashflowData.js:277-478).
- Demo/offline flows are handled locally: App seeds a demo user + plan via `setFullPlanData` when `agentDemo=1` (src/App.jsx:71-89). `useCashflowData` also bypasses Firebase in demo or missing-Firebase paths by reading the persisted store snapshot and writing it back through `setFullPlanData` (src/hooks/useCashflowData.js:524-566).
- UI consumption: App reads the store directly and passes props down; Home pulls selectors from Zustand for all data (src/pages/Home.jsx:61-66). Bills uses store data and uses `useCashflowData` handlers for mutations but not data (src/pages/Bills.jsx:316-337). Planner reads only `userProfile`/`billSharing` from Zustand and receives the rest via props derived in App (src/pages/Planner.jsx:24-41). Accounts defaults to store data but allows prop overrides for tests (src/pages/Accounts.jsx:23-48).

# Store schema + persistence contract
- Initial shape includes profile, planner settings, entities, and UI flags (src/store/useStore.js:7-47). IDs are normalized to strings and Date fields to ISO when lists are set (src/store/useStore.js:49-66, 90-109, 138-142).
- `setFullPlanData` accepts either legacy or current keys: it maps `transactions` or `expenses` to both `transactions` and `expenses`, and `recurringBills` or `bills` to both `recurringBills` and `bills` (src/store/useStore.js:90-109). `plannerSettings` keys are unpacked individually, and simple keys (startDate, startingBalance, income, paySchedule, billSharing, residualAccountId, mode, accounts, goals, categoryBudgets, extraIncomes, allocationRules, paidBills, confirmedDiscretionary, userProfile) are merged if provided (src/store/useStore.js:110-147).
- Persistence partializes to a compact shape: accounts, transactions (prefers transactions then expenses), recurringBills (prefers recurringBills then bills), plannerSettings, paidBills, categoryBudgets, goals, extraIncomes, allocationRules, and mode (src/store/useStore.js:197-212). `merge` reverses that, restoring both legacy and current keys (`expenses` mirrors `transactions`, `bills` mirrors `recurringBills`) and applying plannerSettings defaults while marking hydrated (src/store/useStore.js:214-256).
- `useCashflowStore` wraps persistence to include `confirmedDiscretionary` in the persisted slice and to prefer it from persisted state on merge (src/store/useCashflowStore.js:42-67). It also swaps IndexedDB calls for localStorage or in-memory storage on failure or non-browser environments (src/store/useCashflowStore.js:69-109; src/store/storage.js:7-79).

# Hydration and sync (who writes the store, when, and with what keys)
- Persistence merge: on app load, `persist.merge` reconstructs arrays and plannerSettings, sets `expenses`/`transactions` and `bills`/`recurringBills` together, and flips `hasHydrated` (src/store/useStore.js:214-256). `onRehydrateStorage` calls `setHasHydrated(true)` even on error (src/store/useStore.js:258-264).
- Firebase sync hook: `useFirebaseSync` seeds `userProfile` and registers a Firestore listener; every snapshot with `fullData.data` calls `setFullPlanData(fullData.data)`, letting the store mapping handle bills/expenses aliases (src/hooks/useFirebaseSync.js:56-102). Logout triggers `reset()` to the initial schema with `hasHydrated: true` (src/hooks/useFirebaseSync.js:40-52).
- Secondary Firebase hook: `useCashflowData` spins its own auth + user-doc `onSnapshot`; on snapshot error without cache it reads the persisted store via `selectPlanSnapshot`/`mergeWithEmptyData` and pushes it into Zustand with `setFullPlanData` (src/hooks/useCashflowData.js:468-474). Demo mode and missing Firebase follow the same pattern (src/hooks/useCashflowData.js:524-566). Because this hook is independent from `useFirebaseSync`, mounting both yields two Firestore listeners (one per hook singleton).
- App/UI writers: the App demo effect writes a full plan (startDate, startingBalance, accounts, bills, expenses, income, paySchedule) through `setFullPlanData` when `agentDemo=1` (src/App.jsx:71-89). Settings callbacks also use `setFullPlanData` for income/paySchedule, startingBalance, and billSharing (src/App.jsx:371-375).
- Mutation handlers inside `useCashflowData` optimistically mirror edits into the store: `handleUpdateBills` writes `{...base, bills}` to `setFullPlanData` (src/hooks/useCashflowData.js:624-630). The generic `createUpdateHandler` writes the computed `optimistic` payload to `setFullPlanData`, covering accounts/residualAccountId, allocationRules, goals, categoryBudgets, startingBalance, expenses, extraIncomes, and billSharing depending on the caller (src/hooks/useCashflowData.js:781-793, 831-848). All paths rely on the `setFullPlanData` mapper to normalize ids and sync legacy keys.

# My share vs household total rules
- Canonical helpers: `getScopedBillAmount` (role share math via `percentageSplit` and payer fallbacks) and `isBillVisibleInSelfScope` (role-filtered visibility) live in src/lib/billSharing.js:185-241 and underpin every self-scope view. `getRoleSharePercent` feeds `getScopedBillAmount` for shared/auto bills (src/lib/billSharing.js:185-221).
- Bill summing paths:
  - Home “My Bills Due” filters visible unpaid bills with `isBillVisibleInSelfScope` and sums `getScopedBillAmount` (src/pages/Home.jsx:132-146).
  - Bills page uses `isBillVisibleInSelfScope` for list visibility (src/pages/Bills.jsx:607-621) and sums scoped amounts for totals (all/unpaid/overdue) via `getScopedBillAmount` (src/pages/Bills.jsx:633-645); row amounts also display scoped values in the list (src/pages/Bills.jsx:833-849).
  - Planner derives `myBills` by applying `isBillVisibleInSelfScope` then replacing `amount` with `getScopedBillAmount` before running `projectCashflow` (src/pages/Planner.jsx:65-101).
  - Infographic builds engine bills from live bills; if `personScope === "self"` it filters with `isBillVisibleInSelfScope` and uses `getScopedBillAmount`, but if `personScope === "both"` it bypasses scoping and uses raw `bill.amount` (src/MonthlyCashFlowInfographic.jsx:783-815).
  - UpcomingBills hook filters with `isBillVisibleInSelfScope` and stores `scopedAmount` from `getScopedBillAmount` for each card (src/hooks/useUpcomingBills.js:28-47).
- Labels/scope notes and mismatches:
  - Home card label is “My Bills Due” and matches self-scoped math (src/pages/Home.jsx:132-147).
  - Bills page banner “you’re responsible for” aligns with self-scoped totals; household totals are not shown (src/pages/Bills.jsx:633-645, 700).
  - Planner projection is explicitly “self” scoped by design notes; no household toggle is exposed, so chart/infographic inputs use my-share bills (src/pages/Planner.jsx:36-101).
  - Infographic defaults to `personScope = "self"` but will switch to household totals when `personScope === "both"` because it uses raw `amount`; the UI does not explicitly relabel when switching, so household math could be shown without a clear label change (src/MonthlyCashFlowInfographic.jsx:371-372, 783-815).
  - UpcomingBills hardcodes `scopeLabel: "Self"` and uses scoped amounts, consistent with the helper usage (src/hooks/useUpcomingBills.js:28-48).

# Cashflow engine behavior
- Inputs/outputs: `projectCashflow(params)` normalizes defaults (startDate, months ≥1, empty arrays) then computes and caches results (src/lib/cashflow/projectCashflow.js:193-543). It returns `{ ledger, monthlySummary, finalBalancesByAccount }` where `ledger` entries carry `date`, `kind`, signed `delta`, `balances` snapshot keyed by account in cents, `monthIndex`, and optional `description`/`id`/`isPaid` (opening entry seeded at startDate with delta 0; src/lib/cashflow/projectCashflow.js:381-466). `monthlySummary` is an array of per-month objects with `monthLabel`, `totalIncome`, `totalBills`, `net`, and optional `weeks` buckets populated from ledger deltas (src/lib/cashflow/projectCashflow.js:367-379, 470-522). `finalBalancesByAccount` is the ending balances map in cents (src/lib/cashflow/projectCashflow.js:524-528).
- Units and conversions: All monetary values are converted to cents up-front via `toCents` (opening balances, income per pay, extra income, bills, expenses; src/lib/cashflow/projectCashflow.js:217-242, 258-278, 305, 324) using `formatters.toCents` (src/lib/cashflow/formatters.js:3-7). Ledger `delta`, monthly totals, weekly buckets, and final balances remain in cents; any consumer must divide by 100 (or use `fromCents`) to display dollars.
- Mode rules: In projected mode, all incomes/extra incomes, all bills (paid or not), and all expenses within the projection window are included and deducted/applied (src/lib/cashflow/projectCashflow.js:331-336, 432-435). In actual mode, incomes/expenses are truncated to `date <= todayCutoff` (local vs UTC safe) and bills are filtered to include future bills plus only past paid bills (src/lib/cashflow/projectCashflow.js:330-348). Deduction logic then only subtracts past bills if `isPaid` is true; future bills still deduct (src/lib/cashflow/projectCashflow.js:432-441). “Today unpaid bills” therefore show in actual mode only if their `date` is today or later; if today’s bill is unpaid it survives filtering (future or today) but deducts only if marked paid when `date <= todayCutoff`.
- Cashflow mechanics: Income events allocate to accounts using amount-then-percent rules and residual fallback, adding applied cents to balances and monthly income/net (src/lib/cashflow/projectCashflow.js:402-422, 115-158). Bill/expense events subtract cents from their account (or residual) and add to monthly `totalBills`/net with negative ledger deltas (src/lib/cashflow/projectCashflow.js:425-467). Weekly summaries bucket signed deltas by week-of-month to derive incomeCents, billsCents, and netCents (src/lib/cashflow/projectCashflow.js:470-522).
- Engine invariants: Paid-bill keys are `${billDate}:${billId}` using the clamped bill date per month (src/lib/cashflow/projectCashflow.js:295-309; src/lib/cashflow/dateUtils.js:33-47). Due days are clamped to month length via `getDateForMonthIndex`/`clampDayToMonth` for bills, paydays, and extra-income placement (src/lib/cashflow/projectCashflow.js:231-279; src/lib/cashflow/dateUtils.js:33-47). Events outside the requested month window are skipped (src/lib/cashflow/projectCashflow.js:391-399). Weekly buckets only retain non-zero income/bills/net entries to keep summaries compact (src/lib/cashflow/projectCashflow.js:511-522).

# Cross-page mismatch root causes (grounded)
- Scope drift in Infographic household mode: Symptom—totals jump to full-household amounts while labels still imply self scope. Likely cause—when `personScope === "both"`, bills bypass `getScopedBillAmount` and use raw `amount` without any label toggle (src/MonthlyCashFlowInfographic.jsx:793-815). Evidence—self path calls `getScopedBillAmount`, household path uses `Number(b.amount || 0)`. Repro—demo or live: load Planner/Infographic, switch personScope to “both” (or set prop), compare totals to self mode. Fix—either always scope amounts or surface a clear household label/toggle state.
- Projection-window drift across views: Symptom—Planner chart vs Infographic vs Home show different totals for the same data. Likely cause—Planner calls `projectCashflow` with `months + 1` (src/pages/Planner.jsx:95-114), Infographic hardcodes 14 months (src/MonthlyCashFlowInfographic.jsx:825-839), Home timeline window is dynamic based on today (src/pages/Home.jsx:68-80). Repro—demo or live: set startDate several months back, compare Planner chart, Infographic summary, and Home chart; windows differ. Fix—standardize projection months or expose the window choice consistently.
- Duplicate Firestore listeners: Symptom—two user-doc snapshots run concurrently after opening Bills, risking double updates or racey state. Likely cause—App always mounts `useFirebaseSync` (src/App.jsx:30-33, 277-279) and the Bills page mounts `useCashflowData` which registers its own `onSnapshot` (src/pages/Bills.jsx:332-337; src/hooks/useCashflowData.js:409-478); each module has its own singleton guard. Repro—live: log in, navigate to Bills; observe two listeners in mocked firestore tests or console. Fix—use a single sync hook or share one cross-module singleton.
- Scope consistency drift between Planner and Infographic: Symptom—Planner chart stays “self” while Infographic can render household totals on the same screen. Likely cause—Planner hardcodes `personScope = "self"` for bills (src/pages/Planner.jsx:36-101) but Infographic allows `personScope === "both"` to bypass scoping (src/MonthlyCashFlowInfographic.jsx:793-815). Repro—demo/live: set Infographic personScope to “both”; Planner still shows self projection; compare totals. Fix—lock Infographic scope to Planner’s or provide synchronized scope controls.
- Formatting drift risk in Infographic weekly view: Symptom—weekly bills/income can be double-converted or rounded differently vs engine/Planner. Likely cause—`normalizeCurrencyField` heuristically reinterprets `incomeCents`/`billsCents`/`netCents` even though they already come from cents via `fromCents` for monthly summary (src/MonthlyCashFlowInfographic.jsx:217-334). Repro—demo/live with large integer weekly values; compare Infographic weekly sums to Planner monthly totals; look for off-by-100 scaling. Fix—skip heuristic when keys end with “Cents” or use a single cents→dollars conversion path.

# Recommendations (smallest diffs first)
- Clarify Infographic scope labeling: In src/MonthlyCashFlowInfographic.jsx, surface an explicit “household vs my share” indicator/toggle when `personScope === "both"`; reuse `getScopedBillAmount` for totals when labels imply self. Addresses scope drift and Planner/Infographic mismatch.
- Align projection windows: Make Infographic use the same months window as Planner/Home (or accept a prop) by adjusting the `projectCashflow` call in src/MonthlyCashFlowInfographic.jsx and the `months` argument in src/pages/Planner.jsx to a shared source.
- Single Firestore listener: Choose either `useFirebaseSync` or `useCashflowData` for snapshot subscription, or add a shared module-level singleton so Bills mounting doesn’t create a second listener (src/hooks/useFirebaseSync.js; src/hooks/useCashflowData.js; src/pages/Bills.jsx).
- Normalize currency conversion in Infographic weekly view: Short-circuit `normalizeCurrencyField` when keys end with `Cents` to avoid reinterpreting already-converted values (src/MonthlyCashFlowInfographic.jsx:217-334).
- Add scope parity: Tie Infographic `personScope` to Planner’s scope (prop or shared state) to prevent mixed self/household projections on the same screen (src/pages/Planner.jsx; src/MonthlyCashFlowInfographic.jsx).
